# Project working guide

Current user instructions take precedence. Read the [current plan](docs/plans/joined-plan.md), then use [research/INDEX.md](research/INDEX.md) for the selected task. Historical plans and reports are evidence, not authority. A summary cannot grant permission.

Preserve every goal: wealth, all quests and unlocks, all19 skills at99, best-in-slot gear, useful/rare items, specialist records and the main account rank1 on all24 boards simultaneously. Helper99s are not board wins. Reusable scripts serve these goals.

## Work loop

1. Check branch, dirty/untracked files, process ownership and fresh raw state. Preserve existing edits. One owner controls each account, server and generated output. Use bounded `rg` reads. Narrow truncated output before relying on it.
2. Select a complete capability or its blocking repair. Name the useful game outcome, consumer and owner. Keep ownership through shared-code integration, qualification, release and the next assignment. A small proof is progress toward the capability, not completion.
   Compare ready live work, the largest unlock/supply bottleneck and uncovered game content. Use total acquisition, travel, build and proof cost; state uncertainty. A build's work order must reach its author. Reconnect consumers with explicit queue replacements; do not leave another numbered repair behind failed dependencies. Spend fresh qualification on a finite useful live consumer before another unrelated build.
   Every new build needs a reachable finite live consumer. Promote the existing capability through the contract's definition-update path when its entry or owned helper scope is too narrow. Prove the actual worker CLI; practice-save adapters alone cannot qualify live work.
3. Trace input through caller to consumer. Read exact IDs, event order and APIs before changing waits. After two similar failures, change the method or gather a new observation. Do not restart an unchanged failure.
4. Use the cheapest check that reaches the change, with a timeout. Test relevant adverse cases. Run the applicable integration gate for the final batch. Do not run game suites for documents. Rerun checks invalidated by later edits. Preserve failed results.
5. Inspect final edited files, including untracked files. Report source, proof level, useful output, costs, blocker and next action. Tests, practice, deployment and live results prove different things. Do not count connections, tools, notes or tests as game progress.

On Windows, background subprocesses must use `windowsHide:true` (or the existing hidden launcher). Run only the MCP/services the job needs. Check ownership before stopping processes; Git cache watchers are not Git work. The background-launch regression and native console-visibility check cover the terminal-spam failure.

Use the [script contract](docs/script-contract.md) and its [runnable delivery path](docs/script-contract.md#deliver-a-capability). Parameterize existing workers and promote shared behaviour into its permanent module. A scratch pilot or preset pass is practice-only. Finish through the actual consumer before expanding copies. Keep independent goal lanes moving while finishing the selected capability. The [autonomous coordinator](docs/script-contract.md#autonomous-coordination) owns its durable dependency queue, finite assignments and child processes; inspect its current lease and tasks before taking those resources. Extend existing capability definitions and modules. Do not launch a second controller or duplicate an owned task. Codex and Claude claim planning, build and review work continuously through the coordinator; the five-minute heartbeat is retired. Both share this contract, durable receipts and the existing queue. Check the recorded agent and file/account leases before taking work. Job completion wakes the next dispatch; carry useful output to its consumer and respect stop requests.

Keep plans in the existing task context. Skills support the result; they do not require extra design documents, approval rounds, workers or reflection files here. Ask only for a missing decision that changes the result. Delegate only independent owned work when its benefit exceeds coordination cost. Do not replace the existing harness or create another task board to avoid finishing this path.

## Accounts and allocation

Owner instruction: the PC is available for maximum useful account progress. Fill qualified live slots across skills, quests, combat, valuable resources and endgame supply. Prefer sharks over new trout/salmon surplus; use existing stock rather than discard it. Development slots are separate from live slots. An active build adopts a delivery focus until its first useful live result or three consecutive failed builds. Required supply dependencies and read-only reviews stay eligible; unrelated builds and native refreshes wait. The coordinator may expand capacity in batches of up to4 after two fresh useful live results, prepared demand and measured RAM/CPU/tick headroom. Create additional accounts only with a proved useful first job; never park a claimed identity as progress. The main/fresh scored-launch reservations still apply.

`swarm.json` owns live assignments. `scripts/fleet.ts` contains historical templates; `apply` may only create a missing plan. Review candidate changes before editing current assignments.

New live names: **penis joke plus RuneScape/task/goal pun; optionally Scottish** (owner), 1-12 letters/digits. Preserve existing identities and used role-list order. Check local duplicates; availability stays unknown until registration. Credentials alone do not register an account. First login claims it and spends clock time.

Each assignment has one owner, budget, acceptance and next action. After a batch, reconcile output and assign the next useful conversion, unlock or uncovered skill. Prefer owned stock and trained helpers over surplus or new accounts. Add an account for a missing role, measured bottleneck or fresh-clock record. Keep genuine demand waits and protected reservations explicit. A vacant slot needs a named constraint and next action.

Owner expansion instruction: restore useful existing work, then expand qualified accounts in measured batches. Cap17 is not permanent. Before increasing capacity, check useful output, stalls, RAM/CPU, tick latency, supply throughput and startup/practice reserves. Keep8GiB free and one practice slot. No further permission is needed within these bounds. Reserved or blocked accounts do not count as progress.

## Game and host boundaries

- Practice first, then a bounded live pilot under current authority. Prove applicable entry, work, bank/delivery, refill, recovery and logout. Record missing runtime support. Follow the script contract for unattended qualification.
- Keep the main account offline until its launch gates, actual staging and current-route rehearsals pass. Never use it for tests. Preserve fresh specialist clocks. Specialist wins and the simultaneous24-board goal remain distinct.
- GE buying, selling and merchant trading are authorized (owner). Follow the [market policy](research/supply-logistics.md#market-policy-current). Direct supply transfers require authenticated owned partners. Use AI subscriptions, not paid APIs.
- All gameplay techniques are authorized (owner), including server bugs, login wine, cocktails, pyre oil, Charge, relogs and tick manipulation. No technique needs further approval or community acceptance. Missing supplies create acquisition work, never a route ban. Compare methods by useful output, total cost and observed server behaviour.
- Check admission limits in `scripts/swarm.ts` and `swarm.json`. Measure host load. Run one heavy practice qualification at a time. Do not lower limits to fit a run.
- Honour user pauses across workers and schedules. Stop repeated no-progress attempts. Retain failure evidence. Clear only the exact repaired block after proof. Verification never enables workers or changes repeat policy.
- Never print credentials or copy `bot.env` into evidence. Hide the main account in shareable dashboard views. Preserve pinned upstream code and local patches.

## Keep knowledge small

**No diary.** Docs, plans, research, configs, coordinator work orders and new code comments state what is true now. Git commits are the only history: no dates in prose, `was`/`now` wording, `update` logs, attempt stories or `superseded` findings. Replace a stale fact in place and say why in the commit message. A measurement keeps its conditions (server, tick, script, source) and an evidence path. `bun scripts/check-no-diary.ts` enforces this for Markdown and `swarm.json`.

One home per fact: this guide owns work rules, the script contract owns acceptance, the plan owns priorities, and research topics own findings. Other entry points link there. Aim for under600 words, with actionable blockers and evidence links.

Each finding needs **claim; conditions; evidence; remaining gap or next decision**. Bind results to relevant source, configuration, server and starting conditions. Preserve unaffected proof when inputs change. A speed comparison needs three matched runs per condition, raw times and spread. Test contention separately. Estimates stay estimates.

Keep raw logs and temporary runners in one task folder under `.practice/`. Before removing scratch, check processes, references and recovery needs. Do not hand-edit generated reports. A process change must fix an observed failure and be checked. Remove duplicate or ineffective rules. No process can promise that future agents will follow it. Stop process work once the supported fixes are checked, then deliver game capability.
