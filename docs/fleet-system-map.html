Goals and useful demand

The coordinator values accepted goal effects. Autopilot allocates standing jobs against finite demand. Both use observed evidence.

GoalUseful resultEvidence boundary
Main OverallA fresh rank-one result under the record, after the final route passes its launch conditions.Model ticks, rehearsal ticks, launch permission and a recorded board rank are separate facts.
Specialist boardsFresh owned wins on skill boards with priced route margins.The ledger tracks declared targets. It does not define the complete set of winnable boards.
Every questComplete implemented journal names observed across owned live accounts.Script coverage or a seeded practice completion does not supply a live journal observation.
Useful items and best gearRecent stock capped at named route and army-kit demand, with delivery where required.This finite subset does not define the full useful-item or best-in-slot collection.
PK armyDeclared accounts reach 99 Attack, Strength, Defence, Ranged, Magic, Prayer and Hitpoints, then win against players and hold the Wilderness.The goal ledger measures base levels. Its credited-kill and Wilderness-control fields remain unknown.
  1. Owner goal ledger → coordinator

    Give useful work a value

    The ledger tracks main Overall, priced specialist targets, quests, useful collection items and the PK army. It keeps evidence gaps explicit.

    The dispatcher requires positive goal value. It ranks eligible tasks by goal value per estimated time before model priority.

    Build, qualify, review and provision work inherit value from viable finite run consumers. Rules also need a useful goal effect.

    Unknown observations need a bounded check. Generic capability coverage, extra helper levels and surplus gold do not prove goal progress.

    A bounded GE buy can receive observation support for a finite named supply. The worker checks fresh bank stock before funding. This support earns no acquired-item credit.

  2. Overall route + army → autopilot

    Make only the missing supply

    The Overall planner derives its supply bill from the realistic route and board snapshot. Canonical helper observations show the stock each account holds.

    Stock is last-seen evidence. Reservations, item form and delivery still matter. Autopilot adds eligible army kit needs and finite purchase budgets.

    • firstArmy accounts take useful goal bands. Earlier bands come first. Accounts nearest their targets take places first.
    • thenKit buys and transfers fill missing inputs. Local stock and coins precede cross-side orders. Filler bands use remaining eligible slots.
    • thenSupply jobs earn estimated value over 1,000 ticks. The estimate clips output to unmet demand and subtracts input cost.
    • limitsWaste lowers value. Shared resources lower the value of crowded moves. Hard capacity, holdings, reach and owner claims still apply.
    • pilotsA practice-only template runs live only if the plan's aio list admits its ID. Catalog membership alone grants no live pilot.

    Each assignment reserves expected useful output before the next pick. A vacant slot names its constraint. Gold funds finite consumers.

  3. Worker logs → autopilot

    Use the result to choose the next job

    Autopilot reads matching RESULT and LEDGER lines after each assignment's saved log offset. Status files supply skills and holdings.

    Repeated no-progress failures or excessive waste can retire an account/template pair. Transport drains do not count as worker failures.

    A changed worker script can release a retirement. Death stays held for review. A successful trainer or ended kit buy requests a fresh pass.

How task selection works

The model proposes work. Deterministic code validates the queue, scores useful effects and chooses an eligible task.

  1. Planner input

    Read the gap before proposing work

    The planner reads the goal ledger, account observations, merged plan, queue, outcomes, held builds and repair facts.

    Owner requests bypass normal outcome and idle delays. They still wait for an active planner, resource admission and more than one second since the last round.

    Unconsumed outcomes share a round after a five-minute gap. The idle interval defaults to thirty minutes.

    A proposal names capabilities, dependencies, accepted effects, estimates and reasons. Planning does not log in accounts or execute game actions.

    Graph validation rejects unknown dependencies, cycles, bad account bindings and unsupported capability changes. A new build needs a viable finite run consumer.

  2. Goal value → eligible pool → ranking

    Compare work that can start

    The actual CLI requires positive goal value. Unknown observations and zero useful value both hold dispatch.

    Dependencies and resource gates filter candidates. A fresh qualification can give its first live consumer a turn before another build invalidates the proof.

    preferLive can favour eligible runs. Within the selected pool, goal value divided by estimatedMs comes first.

    Focus then breaks ties. The next score is priority times one plus direct consumers, divided by estimated minutes, plus a capped age bonus.

    The priority-score divisor has a one-minute floor. Goal value still divides by raw estimatedMs. Age adds at most twenty points.

    Creation time and task ID break the remaining ties.

    Estimates are proposal inputs. They are not measured run times. With goal scoring active, there is no guaranteed thirty-minute rotation between goal lanes.

  3. Deterministic rule: next-band

    Continue a useful skill batch without another model call

    The newest finished run must succeed live within twenty-four hours. It must target one skill on one ordinary, unpaused account.

    The capability needs an approved review and a retargetable worker. Separate supply dependencies and an existing open account/capability run prevent another band.

    The rule chooses a method unlock at least five levels ahead. Otherwise it adds ten levels, capped at ninety-nine.

    A source change adds the required qualification refresh. Positive owner-goal value still applies. A failed newest run stops the automatic chain.

    Rules check new receipts or each five minutes. Models and owner proposals still supply new methods, builds, repairs and other task graphs.

Task types and saved states

The queue connects preparation to a finite live consumer. It also retains failed and replaced work so a restart cannot erase its meaning.

KindWorkResult passed to consumers
buildAuthor declared files in an isolated workspace. Run delivery and applicable review. Publish only the owned source.Delivery fingerprint, runtime source, review and publication evidence. A build is not a live run.
qualifyRun the existing capability's native delivery checks on its current source.A source-bound delivery result. Qualification does not author code or enable a worker.
reviewIndependently inspect source, callers and proof. Do not edit or launch work.Approval or a concrete rejection tied to the reviewed source.
provisionReserve and register one ordinary account for a prepared first job.A confirmed identity that accountFrom or @task-id participants can resolve.
runInstall a finite coordinator job, wait for accepted live effects and disable that owned job at the end.A live receipt with source, target account, status and acceptance outcome. Recovery is a distinct supported run path.
  1. Submission → pending → running

    Keep one attempt identity

    A valid submission enters pending. Dispatch changes it to running with a new run ID, start time, attempt count and worker owner.

    The run folder retains its input, logs and receipt. A process restart reconciles those files with the saved queue.

    Most dependencies need success. Recovery ordering edges can instead wait for an earlier recovery to end, so one failed account cannot strand all others.

  2. Matching receipt → succeeded / failed

    Settle the queue item

    Task ID, run ID and receipt time must match the active attempt. The receipt selects succeeded or failed.

    A vanished child without a receipt fails after startup grace. A matching late receipt can repair that missing-receipt classification.

    A supported ordinary run can return to pending if it installed no job and encountered a validated session, autopilot or memory wait.

    That wait retains its raw receipt. It does not count as useful live success.

  3. Replacement / retirement → superseded

    Repair the graph without erasing evidence

    Explicit replacements reconnect pending consumers to compatible tasks. Failed receipts remain. Replaced pending work can become superseded.

    Provision tasks cannot be replaced. Cancellation must not strand pending dependants or an account reference.

    Old ordinary work behind dead dependencies can retire under its age rule. Main and specialist launch tasks remain protected.

    Finished tasks older than two days can move to archive/tasks.jsonl. Open references and the newest result of each capability/kind retain their records.

Queue counts measure orchestration. A successful provision, review or build does not increase the count of completed quests or prove a useful item reached its consumer.

The account life cycle

An account needs a useful first job, a registered identity and one owner. Credentials alone do not make it ready to play.

  1. Prepared consumer → provision task

    Prove why this account should exist

    A pending first run must have current native delivery proof. Its fingerprint and runtime revision must match the installed source.

    Review holds and participant admission still apply. Prepared peers need the correct side, credentials, settled sessions and room within the job's account limit.

    A pause, conflicting assignment or unresolved repair holds creation. A composed assignment must keep all its participants.

    The coordinator creates new ordinary accounts through this path. Main and specialist accounts have separate protected launch rules.

  2. Reviewed name list → shared reservation

    Reserve one identity

    The role's name list supplies the first unused name, compared without case. Automated provisioning requires one to twelve letters or digits.

    Local identities and names reserved by existing jobs are excluded. The coordinator saves identity.json before the shared owner reservation.

    A definite reservation conflict permits the next name. An uncertain reservation stops with the selected identity retained for review.

  3. Credential creation → bounded registration

    Register, then confirm logout

    fleet.ts create creates or restores local credentials. It does not register the account or install its first job.

    Provisioning then makes one bounded registration attempt. The default deadline is sixty seconds. The claim worker does no tutorial or useful game work.

    Success needs exit zero and one valid CLAIM … logout=logged-out line. The coordinator retains the registration result in claim.json.

    A timeout, failed process or missing confirmation leaves availability unknown. It must not silently create another identity for the same uncertain attempt.

    The first login starts the account's live clock. Registration is not a free preparation step for a scored account.

  4. Confirmed identity → account assignment

    Choose the account's work owner

    A successful provision receipt can resolve accountFrom or an ordered participant reference such as @provision-task.

    Autopilot plans correct-side accounts with its own marked job or no named job. Enabled hand jobs and coordinator assignments keep their accounts.

    Reservations, owner pauses and plan ownership prevent takeover. A disabled marked job keeps its pause and repeat settings when its template changes.

    The army roster opts accounts into goal bands. Per-account builds constrain levels and quest routes.

    Template requirements check skills, combat, quests, quest points, food and kits. Practice-only templates also need the plan's explicit pilot opt-in.

  5. Admitted job → claimed session → settlement

    Run under one owner

    The job admission path checks the account and host. The connection takes its shared claim and records the exact attempt before network use.

    The worker records observed progress. Its supervisor classifies the end. Logout proof must match this session.

    A successful finite job can release the account for its next band or consumer. A standing job follows its own repeat policy.

    A pause keeps the account held. A failure can need repair. Neither state is permission to reassign or log in the account blindly.

  6. Side handover / credential restore

    Keep identity across machines

    fleet/owners.json names the side allowed to use the account. Credentials and vault access do not override that ownership.

    When a credential is missing and the vault restores none, FLEET_SEED derives its password from the lower-case server and account name.

    Without a seed, local creation uses a random password. Coordinator provisioning on a cloud side requires the seed.

    The encrypted vault can restore a missing credential without overwriting an existing file. The main account is excluded from sealing.

    Adoption and return transfer eligible owner rows through a confirmed shared push. They do not create a new account or reset its clock.

A job becomes a bot

The swarm controls starts. The worker owns its session. The producer records what the server confirms.

goes onnext stepwaitsdepends on a clearing eventretriesbounded repeatholdsrepair or owner action needed
  1. Three plan writers

    Install one assignment

    Owner and agent sessions edit swarm.json. Autopilot replaces only its side's marked jobs. Coordinator runs write .practice/coordinator/jobs.json.

    The root swarm merges both files. Coordinator jobs take their accounts from overlapping owner jobs. A custom practice plan runs without that overlay.

    Coordinator jobs use repeat:false and maxRestarts:0. Standing owner jobs have separate retry and release rules.

  2. Swarm

    Check account and host admission

    • holdsA reservation, wrong side, stop file, failed-script hold or unresolved repair blocks a start.
    • waitsA non-standing job waits for the runtime build lock. A coordinator-scoped swarm admits only qualified coordinator jobs and standing jobs.
    • waitsA running mission keeps the account. A fresh external status blocks a second login. Demand-only jobs wait offline when there is no demand.
    • waitsAdmission counts managed, external and starting accounts against maxBots. Recovery can reserve one slot.
    • waitsProjected free memory must retain max(4 GiB, minFreeGB). A new process reserves 1 GiB for 30 s.
    • holdsSession admission checks the exact account's logout proof. Unknown or crossed session evidence refuses a later start.

    Hosted or orchestrated participants share one startup heap reserve. Each account still counts toward maxBots. The swarm itself does not test CPU/tick headroom.

  3. Swarm → supervisor → worker

    Start a detached process

    A normal job uses supervise.ts. An orchestrate:true job uses that supervisor with all participants and defaults to zero restarts.

    A host:true job uses supervise-host.ts, then one host process. Normal jobs default to 20 restarts.

    The worker can be a direct script, AIO, chain or host. AIO dispatches a category or pipeline. Every job need not pass through AIO.

    The swarm saves the detached supervisor's PID, accounts, mission, log and offset. A replacement swarm adopts those runs.

  4. openBot → connectInProcess

    Cross the network boundary

    The worker checks side ownership, credentials, live permission, launch gates, stop files and the controller lease. It checks the source release where required.

    Standing jobs skip source-pin equality and the build-lock launch check. Main and specialist launch gates still protect their clocks.

    The connection claims the account and writes its session attempt before network use. A held claim can stop a login.

    Three consecutive held-claim refusals end an eligible supervisor retry streak. Coordinator jobs with zero restarts can end earlier.

  5. Worker session

    Play, observe and settle

    Default status writes occur each 5 ticks and each 5 s. Tick recording is enabled by default, with TICK_RECORD=0 as its off switch.

    Each 25 ticks, the worker checks stop files and its controller lease. The default no-progress limit is 900 ticks.

    A clock watcher ends a silent tick stream after the configured limit, default 120 s. A transport failure can retry within the supervisor budget.

    The worker reconciles its outcome and closes its session. Only this attempt's server-confirmed logout supplies producer logout proof.

  6. Supervisor → swarm

    Classify the end

    • doneExit 0 plus RESULT ok ends successfully. Repeat policy or a changed successful mission can permit more work.
    • holdsDeath, missing requirements, no progress or repeated matching failures stop blind retries. Empty food ends stopped and needs supply.
    • waitsRelease holds end release-paused. A refusal before any game tick ends refused. Their next starts still need valid admission.
    • retriesOther failures wait 10 s. A ledger with at least 300 ticks sets the failure streak to one. The retry cap still applies.
    • standingStanding jobs can clear blocked, gave-up, lost and qualifying stopped ends. Empty-food and death ends stay held.

    Standing retry needs a finished live status quiet for 15 min, or matching logout proof at least 2 min old. Owner stops still block starts.

    The swarm records ends in swarm-deaths.json. Coordinator acceptance also checks identity, source, freshness, useful effect and settled participants.

Inside a worker

The planning models choose work outside the game loop. Worker code sends actions and reads game state through the SDK.

FormWhat it doesBoundary to keep in mind
Direct scriptRuns a specific skill, quest, supply, combat or observation worker with its own arguments and stop contract.Each script defines its target. A script file alone is not a qualified capability.
AIODispatches skiller, fighter, boss, pvp, quester, market and logistics categories. Its pipeline compiler can choose job steps.AIO reuses workers. It does not replace the coordinator, swarm or account admission.

  1. Worker → openBot → in-process session

    Use the game client

    BotSDK reads state. BotActions supplies actions. A shim joins both to the LiteClient in the same process.

    The normal worker path does not require a browser, an MCP call or a separate SDK gateway for each game action.

    The game server owns the result. A sent click, queued action or completed helper call does not by itself prove the intended effect.

  2. Ticks, navigation and guards

    Act on observations

    Game ticks publish state and wake waits. Worker code checks skills, items, location, dialogue and other state before its next action.

    Route search can run in a separate worker so a cold path search does not stop packet handling.

    Shared helpers can handle food, prayer, events, loot, escape and death recovery. Their flags and script exclusions control which guards run.

    Replay, practice and scored runs have different controls. A replay uses recorded accounts and must not fall through to a real login.

  3. Worker → status, ledger and settlement

    Report the effect, then close the session

    Status holds observed skills, stock, journal and counters. The tick ledger classifies XP, inventory changes, movement, animation, dialogue, stun and idle time.

    An inventory change can be a withdrawal, trade or consumption. The ledger does not treat every change as net production.

    Settlement prints the ledger, attempts logout and closes the client. Failed logout or timed-out close changes the final result to failure.

    Only after settlement does the worker print its final RESULT. Tick records retain observed state and commands for replay.

Coordinator work

One queue connects code, practice proof and a finite live consumer. A passing diagnostic alone cannot complete a delivery.

  1. Planner, rules and owner requests

    Add useful tasks

    A planner round can follow a request, a failure, an outcome without a consumer, or the idle interval. Rules also add tasks without a model call.

    Proposals must name known capabilities, valid dependencies and finite consumers. Replacements reconnect pending consumers while retaining failed receipts.

    Planner failures back off from 1 to 30 min. A usage limit can select the other model. Model choice also considers current work.

  2. Dispatcher

    Choose work that can start

    Positive goal value per estimated time guides eligible choices. Dependencies, account ownership, qualifications, review, memory, disk and source ownership remain gates.

    • waitsUnder 2 GiB free disk, new tasks and planning wait. Shared-file builds run one at a time.
    • waitsTwo matching build failures hold a capability for 24 hours. A build with newEvidence can cross that first hold once.
    • waitsA third matching failure retains the hold. A rejected review holds later runs on the reviewed source. Changed source still needs fresh qualification.
    • retiresOrdinary pending work behind a dead dependency can retire after 24 hours. Protected main and specialist launches are excluded.
  3. Build worker

    Write code, then check the delivery

    A capability build has an isolated workspace and owned files. An explicit model choice wins. Otherwise build counts balance Claude and Codex.

    Authoring permits at most three turns. A declared practice diagnostic can return observations during a turn. It cannot complete delivery.

    The author's diagnostic helps find defects. Full delivery still checks regression, practice and the consumer against the exact source.

    Only a failed regression can trigger automatic code repair in that delivery loop. It must be non-timeout, with repair enabled and fix rounds remaining.

    Practice and consumer failures return to the integrator for diagnosis. A useful retry needs the cause, the smallest repair and fresh proof.

  4. Replay + review

    Decide whether review blocks delivery

    Review prefers the other model. A recognized usage limit can select the fallback model within the same budget. Deferred review becomes a separate task.

    Native qualification must pass first. Changes within owned files can deliver before review if three required recorded runs replay cleanly.

    replayAllow can permit named command types to change. Replay counts those changes and continues checking later commands.

    Unknown scope, too few records, replay errors or disallowed differences require review before delivery. A later rejection holds subsequent capability runs.

  5. Build publish

    Write the owned source into main

    The worker takes the build lock. It can copy unchanged-base files or merge supported earlier deliveries. Overlap or unowned edits refuse publication.

    An unchanged prepared source can resume without another author pass. Delivery and applicable review still run again before publication.

    Standing workers can continue during a publish. Non-standing starts wait for the lock. Publishing source and merging its pull request are separate steps.

  6. Qualification → run

    Prove this source, then use it

    Qualification binds a capability fingerprint. A source change requires fresh proof for waiting live consumers. The coordinator refreshes demanded capabilities.

    A run installs its job, waits for source-bound useful acceptance, and disables its own job when it ends.

    An explicit timeoutMs controls the window. Otherwise the fallback uses 1.5 times the estimate, at least 15 min, with a maximum cap.

    Missed targets or an expired window produce a failed receipt. They can request a planner diagnosis and a changed finite consumer.

What counts as proof

Evidence answers one question at a time. Source behavior, a passed practice case and a useful live result are separate claims.

EvidenceWhat it can establishWhat still needs a check

Unit / regression / typecheckThe checked code satisfies that test or type contract.Native game behavior, full route conditions and useful live output.
Practice / AIO benchThe worker reaches a declared target in the checked practice state and seed.Live procurement, travel, fresh clocks and behavior outside that fixture.

Session / trade receiptExact session logout, or the proved movement and bank effect of a named transfer.A logout proves session end. A command acknowledgement or an old stock row does not prove delivery.
  1. Coordinator acceptance

    Bind the result to this run

    The status must name the target account, live server, run identity and exact worker revision. It must start after installation.

    Its timestamp must fall within this run and be no more than five minutes old. Its result must begin with ok.

    Skill targets are minimum levels. Bank targets require a bank observation from this run. Quest targets need complete journal flags.

    Counters must meet their declared values. For a group, acceptIndex selects whose effects are checked. Every participant also needs an end record after installation.

    The group end check does not independently require each participant's result to succeed.

  2. Stock, source and useful effect

    Keep the limits visible

    Bank targets check the held total, not an automatic production delta. Named acquisition workers need their own movement and provenance checks.

    A last-seen bank observation can help planning. It does not prove that stock is still present, free, reachable or received by its consumer.

    Capability fingerprints, worker import revisions and controller launch revisions bind different source scopes. One Git commit alone does not replace those runtime checks.

    The goal ledger credits only evidence that meets each goal's rules. Scored launches, player kills and Wilderness control need their own bound proof.

Code reaches the fleet

A merged change needs an eligible checkout move. Existing processes and fresh starts can load different source.

  1. Agent session or coordinator delivery

    Check and merge the change

    An agent session opens a pull request from its branch. The coordinator can stage published deliveries against origin/master and open their pull requests.

    An agent or person runs the applicable gate. Code needs complete type-check and test evidence. No repository daemon merges pull requests.

    ci-gate.ts --post posts its status on the checked commit. The hosted workflow also needs an explicit start.

    Conflicts and failed checks need repair. Merge alone does not prove the main checkout or a live worker uses the change.

  2. Fleet agent → live-update

    Move master without losing local work

    • holdsLIVE_UPDATE=0, its stop file, a non-master checkout, or local commits ahead prevent an automatic move.
    • waitsA build lock, pending publish or overlapping build-owned file holds the move. A qualification holds relevant changed source.
    • waitsA live non-standing session holds files its entry loads. This includes manual sessions. Standing sessions are exempt from release-equality waits.
    • manualAn incoming dependency manifest needs a manual checkout/dependency update. Running bun install alone does not clear this incoming-file guard.
    • adoptsA dirty copy of a verified merged delivery can be adopted. A supported unmerged delivery edit can survive a clean three-way rebase.
    • holdsOther conflicting local edits stay in place. The result names the reason. Unrelated dirty files need not block the move.

    If the SDK patch changes, an exact patched or clean vendor tree can receive it. Other vendor edits or new-file collisions are preserved and reported.

  3. live-update → daemon reload

    Reload only affected loops

    .practice/live-update.json names daemons whose import closure intersects the changed files. Later unrelated updates retain each pending reload request.

    Autopilot restarts after its active pass. Fleet-agent restarts after its active trades. A coordinator restart retains running task workers.

    The dashboard collector closes its event streams and finishes active requests before starting its replacement. The publisher reloads between cycles.

    If swarm source changes, the coordinator can replace a detached-run controller without pausing or draining its sessions. The replacement adopts detached supervisors.

    A legacy controller can need a drain. The bounded standing drain has a 5 min limit and 1 hour backoff.

    Existing sessions retain loaded code. Fresh worker starts load disk source and apply their job's release and launch rules.

How supply work is chosen

A missing item is a finite acquisition problem. Demand, observed stock, funding and transport all belong to the same consumer path.

  1. Route / army / finite production consumer

    Count the shortage

    The route bill and army kits name wanted items. Account observations show last-seen pack, worn and bank stock.

    Reservations, donor reserves and accepted input forms reduce what is available. Old or unknown stock needs verification before another acquisition.

    A production template sizes its order to demand, its maximum and available inputs. It reserves required inputs and marks the job finite.

    The planner reserves expected output before its next choice. The 1,000-tick value estimate is separate from the worker's actual quantity and stop contract.

  2. Autopilot source choice

    Use reachable stock before buying it again

    Available spare stock on this side precedes a repurchase. Donors keep required kit and cash reserves.

    An affordable local purchase can precede a remote transfer because remote orders retain their sync lead. Shops and self-supply have separate worker paths.

    A donor must be available for its transfer. It does not receive another conflicting assignment during that pass.

    A running band, open purchase or productive remote recipient can keep its assignment. A waiting transfer must not park useful local work without cause.

  3. Finite funding → acquisition → delivery

    Close the whole supply path

    A named purchase budget gives coins a use. Local funds, owned donors or a finite earning helper can cover the shortfall.

    Quote-based acquisition selection needs a current ask and observed seller count. A quote is not a filled order.

    The buyer can submit a bounded limit order. It checks the bank baseline, purchase cap and reconciled movement.

    Transfers need the order and receipt path below. Production needs confirmed output. The consumer still needs the delivered item in its required form.

    Held stock, reserved stock, banked output and staged supplies are different states. A preparation report is advisory until its delivery and staging proof pass.

Items between sides

Each side logs in its own accounts. Shared orders and exact receipts connect the two halves of a trade.

  1. Owner, route staging or autopilot

    Write a finite order

    An order names giver, receiver, server, item lines, counts, time window and optional meeting tiles. Varrock West is the default meet.

    Autopilot uses finite coin or kit demand. Its army item orders meet at Ardougne north bank. Both participants stay available for the order.

  2. fleet-sync

    Share the order and observations

    Sync uses the separate .practice/fleet-data worktree. It pulls with rebase and autostash, writes this side's data, commits, then pushes.

    It shares snapshots, merged plans, resource claims, side cards, orders and receipts. Newer prior observations survive a fresh container or account handover.

    Conflicts stop the sync before staging. The result keeps the failure visible. A later fleet-agent pass can retry.

  3. Fleet agent → fleet-trade

    Use an idle owned account

    Enabled owner or coordinator jobs make the account busy. Owner pauses, unsettled runs, logout evidence and shared claims can also block it.

    The worker rechecks admission within the order window. It writes a prepared receipt before network use.

    The giver confirms its bank debit and pack credit. The receiver accepts exact item counts, deposits the received items, then confirms the bank credit.

  4. Trade worker → sync

    Settle with proof

    • settledExact requested counts, receiver bank credit and matching confirmed logout support settlement. Sync publishes the terminal receipt, then releases its matching claim.
    • failedConfirmed logout and known zero movement support failure. Sync can release that matching claim after publication.
    • reconcileUnknown movement or missing logout stays explicit. Proved zero-movement cases below can release held claims. Other cases need reconciliation.
  5. fleet-sync

    Release proved trade claims

    Each case needs a matching held claim and version 2 receipt, zero count, and no observed inventory change.

    • case 1A terminal failed partner receipt proves zero transfer. The own receipt must show an ended worker, or a prepared claim/window must be an hour old.
    • case 2No partner receipt exists after the order window. The own receipt is reconcile. The partner side publishes at least 2 min after the window ends.
    • case 3The own ended receipt proves no trade screen opened. The order window has ended. No partner receipt is needed.
    • case 4Both participants belong to this side. Their matching reconcile receipts show an opened trade screen and zero movement for every ordered stack. The order window has ended. Current producer logout proofs match both claims, and both processes have ended. Sync releases the two claims in one atomic push. A changed claim refuses the pair. The raw receipts remain reconcile.

    Case 2 uses the local clock for a partner on this side. Other unresolved trade claims have no expiry. Do not infer settlement from elapsed time.

Watching and control

The dashboard joins evidence. The publisher separates owner control data from its public projection.

  1. Local dashboard

    Show evidence with its age

    Default address is 127.0.0.1:3100. The dashboard joins local status, canonical fleet snapshots, world feed, boards, process state and coordinator evidence.

    It builds shared state each 2 s while watched. Remote snapshots, observed positions and fresh local sessions carry different freshness and proof.

    Responses mask the main account's name. Local control checks the session and loopback origin. DASH_READ_ONLY=1 blocks actions.

  2. Publisher → hosted views

    Publish the right projection

    The publisher writes local output each cycle. With a configured repository, it publishes private control.json to data.

    The public site projection excludes main/reserved/practice accounts, banks, private task text and income. Carried inventory remains visible, including carried Coins.

    Public pushes are at least 10 min apart by default. A cold dashboard can wait for prices and rivals before its first public push.

    If public text still names the main account, that projection fails. Owner control can still publish. The daemon logs the error and retries later.

  3. Owner → publisher → local control

    Apply a command once

    The hosted owner page commits a command file. The publisher polls it during the next completed cycle.

    It checks owner identity, ID, age, account and prior receipt. Commands can pause/resume accounts or the swarm, pause the coordinator, change jobs or request planning.

    Coordinator console commands can queue proposals. A command receipt records the outcome. Resume removes only the supported command's own hold.

    A command receipt proves its control effect. It does not prove useful game output or successful live work.

Limits and proof

The source contains repair paths and clear limits. It cannot promise that every future fault will repair itself.

  • Goal-scored dispatch has no guaranteed lane rotation. The highest useful effect per estimated time wins within its eligible candidate pool.
  • A deferred review is queued after delivery. Without a viable pending run linked through that review, it can receive zero goal value and remain undispatched.
  • A prepared first job does not alone make provisioning dispatchable. Before its identity resolves, skill or bank effects can have unknown value. Remaining quest effects can provide value before account binding.
  • The goal ledger leaves the full specialist and collection scope unknown. Its player-kill and Wilderness-control metrics are unimplemented, and its overall done value remains false.
  • Agent sessions or people start the required gates, resolve pull request conflicts and merge changes after checks pass.
  • An incoming dependency change needs a manual checkout and dependency update. Its manifest guard does not watch for an install to finish.
  • An unresolved trade claim outside the proved dropped cases needs item/session reconciliation and release of the exact claim.
  • A failed recovery needs diagnosis, a repaired method, fresh practice evidence and a finite consumer. Old failure evidence remains visible.
  • Main and specialist launch gates protect scored clocks. Tool access, higher levels and practice proof do not grant a scored launch.
  • Host expansion needs useful demand and measured headroom. Per-start swarm memory checks do not establish CPU or game tick headroom.
  • Generic coverage describes capabilities. Goal completion needs accepted evidence for each owner goal, including player kills and Wilderness control.
  • The implemented goal ledger keeps unproved results explicit. This page makes no claim that the overall goal is complete.
